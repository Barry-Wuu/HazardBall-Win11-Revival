# Hazard Ball Win11 Revival

把 2004 年的弹珠物理游戏 **Hazard Ball** 复活到现代 Windows（Win11）。

> Hazard Ball（aka **Hazard：Chris' Golf Ball Puzzle**）是英国开发者 Chris Eastwood 的作品，
> 2004 年发行。玩家操控一颗弹珠在各种机关迷宫中滚动，多人模式支持同屏对战。

```
双击 开始游戏.bat
```

## 问题 1：coop10 双人出生点残缺

### 现象
多人模式最后一关 **coop10「TEMPLE OF DOOM」**，两个球的出生点各缺一角，缺口处夹着岩浆，球一出生就卡死。

### 根因
`.map` 格式（`tools/hz.py` 已解出）中，出生点用 terrain 编号标识，每点占一个 2×2 的 4 格：

| 玩家 | 2×2 排布 |
|---|---|
| 玩家 1 | `6 7` / `8 9` |
| 玩家 2 | `2 3` / `4 5` |

全 127 张地图扫描（`tools/scan_ck.py`）显示：**只有 coop10 的两个起点块残缺**，其余全部完整 2×2。
两处缺的都正好是**左上角（a 角）**：

| 起点 | 缺失格 | 原值 |
|---|---|---|
| 玩家 1（terrain 6-9） | `(55,17)` 应为 `6` | 普通地板 `50` |
| 玩家 2（terrain 2-5） | `(58,17)` 应为 `2` | 普通地板 `50` |

两个起点块被第 57 列的岩浆隔开——正是残缺导致的死亡夹角。

### 修复
`tools/fix_coop10.py`：只改 terrain 两格（文件偏移 2093 / 2096），原版备份为 `DATA/coop10.map.orig`。

验证：修复后 `scan_ck.py` 报「全部 coop 地图起点均为完整 2×2」。

## 问题 2：Tilt and Roll 模式用空格跳跃

### 现象
Tilt and Roll 模式（游戏状态 25）需要一款 **PS3 SIXAXIS 六轴手柄**才能跳跃。
游戏在 DirectInput 里只认「3 轴 0 按键」的 gamepad 指纹，普通键盘/手柄都不行。

### 根因（capstone 反汇编 `Hazard.exe`）
- 输入对象 `[0x44BC2C]`：`+0x000` 键盘 256 字节（标准 DIK 扫描码，空格 = `0x39`）、
  `+0x10C` 手柄、`+0x110/+0x114/+0x118` = 手柄 lX / lY / **lZ**。
- 跳跃有**两个闸**必须同时成立：
  1. `[obj+0x161]` 标志（由手柄轮询置位，`0x408720`，阈值 |轴| > 50）
  2. **lZ 绝对值 > 240** —— 这才是「猛然抬起传感器」的真身
- 方向取自 lX / lY（配 `+0x110/+0x114`）。
- 额外坑：`0x40759A` 处检测「当前是否按着方向键」，**按着就绕过整个跳跃判定**
  → 键盘玩家即使拿到标志也永远跳不了。

关键字符串坐实语义：
- `TIP: LIFT THE TILT SENSOR FIRMLY TO JUMP (WHILST MOVING)`
- `USB TILT SENSOR NOT DETECTED` / `WITH A 3-AXIS TILT SENSOR`
- `PERFECT JUMP!!!`

### 修复
**不碰手柄识别**，只把「抬起传感器」这个动作改用空格触发。补丁（`tools/build_patch.py`）：

- 钩点 `0x40759A`（整段 28 字节）→ `JMP 0x442F15`
- 桩代码 175 字节置于 `.text` 尾部空地，并将 `.text` 的 `SizeOfRawData`
  由 `0x41F15` 抬到 `0x42000`（正好贴住 `.rdata`）使其被映射、可执行
- 桩逻辑：**空格上升沿** → 用球的当前速度方向合成 lX/lY（除以较大分量再 ×200，
  **方向自动跟随移动方向**，不依赖世界坐标正负）→ `lZ = 255` → 走原版起跳流程
- 顺带解决「按着方向键也能跳」（原版做不到）

设计取在坐标系无关的位置，因此不依赖关卡几何。

### 已知取舍
- 空格跳跃**取代**了原手柄路径——真接上六轴手柄也不再触发跳跃（保留手柄路径需另加分支）。
- 边沿触发：按住不放只跳一次，松开再按才再跳。

## 问题 3：窗口模式鼠标坐标错位（分身 / 点哪都出界）

### 现象
窗口模式下，把游戏窗口放到**屏幕中间**后：
- 屏幕**左上角残留一个鼠标分身**（真光标被拽到游戏窗口外）
- **点任何菜单都会跑到外面**
- 鼠标移动时**闪烁**（在边界反复被拽回）

### 根因
游戏的整套坐标**硬编码假设「客户区在屏幕原点 (0,0)」**：

1. `CreateWindowExA`（`0x423AF3`）传入的窗口 X/Y **就是 0**
   （`0x423AE1/0x423AE2: push ebx`，ebx=0）—— 游戏主动要求窗口在原点
2. 每帧 clamp（`0x41C0D0`）拿 `GetCursorPos` 的**屏幕绝对坐标**，与硬编码边界比较：
   `.rdata` `0x4433A4 = 25.0` / `0x4433A0 = 600.0` / `0x44339C = 440.0`
   —— 这是 **640×480 客户区的窗口内逻辑框**（600 = 640−40，440 = 480−40），
   **完全不含窗口屏幕原点**
3. 越界即 `SetCursorPos` 拽回

窗口被放到中间时 `clientOrigin = (401,241)`，clamp 区间 `X[25,600]` **整体落在窗口左侧**。
运行时实测：OS 光标被锁在 `(247,392)`，而窗口左边界是 `401` —— 光标在窗外 154 像素处。

**全屏时这个假设天然成立**（客户区就是屏幕，原点 0,0），所以这是典型的
「按全屏思维编写、窗口模式未做坐标转换」的老游戏通病。

### 解法（已定案，零 exe 改动）

**让窗口待在 (0,0)** —— 游戏的原生要求。

`dgVoodoo.conf` 保持默认 `CenterAppWindow = true` 即可：实测 dgVoodoo 在本作**不会**
强制覆盖游戏指定的初始位置，窗口稳定停在 (0,0)。已连续重启 3 次验证：
窗口均在左上角、菜单可正常点选。

> **为什么窗口不能放中间？**
> 想让窗口正中，必须把 clamp、菜单命中检测等**所有**硬编码坐标改成窗口相对
> （`org + 25` / `org + 600` …）。本次曾尝试三版窗口相对化补丁均未生效——
> 因为菜单命中检测是独立的 (0,0) 假设，只改 clamp 不够。
> 若确需窗口居中，可在此基础上补一层坐标转换（hook `GetCursorPos`/`SetCursorPos` 做 ±clientOrigin），
> 工具链已就绪（`tools/hdis.py` / `refs.py` / `relcall.py`），
> `.theta` 段 `0x4748D9` 起有约 1.8 KB RWX 空闲可放 trampoline。

### 排查过程中纠正的三个错误结论（记录以免重蹈）

1. **误按标题匹配窗口**：`GetWindowText` 抓到同名的
   `CabinetWClass`「Hazard Ball」**文件选择对话框**（1455×927，pid ≠ 游戏），
   据此误判窗口位置。**必须用 `class='winclass'` + 客户区尺寸（638×478）过滤。**
2. **误判 recenter 是干扰源**：实测 `[0x44BC58]/[0x44BC5C]` **全文件无任何写入点**，恒为 0，
   故每帧 recenter（`0x40EB10`）目标 = `X + 0.03×155×0 = X`，是**空操作**。
   「闪烁」实为 clamp 在居中窗口下频繁触发的固有行为，与补丁无关。
3. **只改 clamp 就以为能修好**：菜单命中检测是另一处独立的 (0,0) 假设。

> 教训：窗口/坐标类问题**先跑实机窗口枚举 + 读运行时全局**（`ReadProcessMemory`）
> 再动手。静态反汇编只能告诉你「代码写了什么」，不能告诉你「实际发生了什么」。

## 工具链

| 脚本 | 用途 |
|---|---|
| `hz.py` | `.map` 格式解析（tileset / 尺寸 / 关号 / terrain / cells） |
| `scan_ck.py` | 扫描全部 coop 图的双人出生点完整性 |
| `fix_coop10.py` | 补齐 coop10 两处残缺起点（幂等 + 备份 + 校验） |
| `build_patch.py` / `build_stub.py` | 生成 Tilt-and-Roll 空格跳跃补丁 |
| `hdis.py` | capstone 反汇编封装（`python hdis.py <起址> <止址>`） |
| `refs.py` | 定位某地址的全部引用点 |
| `relcall.py` | 暴力扫描 `E8`/`E9` 相对调用（**比线性反汇编可靠**） |
| `callfind.py` | 查某函数的调用者 |
| `peek.py` / `pe_info.py` / `import2.py` | PE 段表 / 导入表（IAT 地址）解析 |
| `strings_hz.py` | 关键词字符串提取 + xref |
| `vtcall.py` | 统计 COM vtable 间接调用 |
| `fix_clamp.py` | clamp 窗口相对化（**实验性，未启用**，见问题 3 说明） |
| `pin_window.py` | 把窗口钉到 (0,0)（`--show` / `--once` / 常驻） |
| `revert.py` / `revert_clamp.py` | 一键还原（全部 / 仅 clamp 补丁） |

依赖：Python 3.11+；`pip install capstone keystone-engine`（仅打补丁时需要）。

### 复现

```bash
# 1. 校验 coop10 出生点完整性（当前应报全绿）
python tools/scan_ck.py

# 2. 若从原版 coop10.map.orig 恢复并重新修复
python tools/fix_coop10.py

# 3. 从 Hazard.exe.orig 重新生成跳跃补丁
python tools/build_patch.py

# 4. 一键还原全部补丁
python tools/revert.py
```
